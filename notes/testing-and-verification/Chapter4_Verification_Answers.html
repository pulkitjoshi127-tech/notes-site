Q1What is a Testbench? Explain the Importance of Verification.5 Marks

Testbench

A testbench is a piece of code (HDL/HVL) written around the Design Under Verification (DUV/DUT) that is not synthesized into hardware, but is used purely to verify the design's functional correctness in simulation. It generates stimulus, applies it to the DUT, monitors the DUT's responses, and checks them against expected behaviour.

Fig: Testbench applies stimulus to DUT and checks responses via monitor/scoreboard

Importance of Verification

  • Modern SoC designs are extremely complex — a single unverified bug can cause costly silicon re-spins (millions of dollars, months of delay).
  • Verification typically consumes 60–70% of the total design cycle time/effort, reflecting its critical role.
  • Ensures the design meets its functional specification before committing to fabrication.
  • Early bug detection is far cheaper than post-silicon debug (analogous to the Rule of Ten in testing).
  • Builds confidence for tape-out sign-off through measurable coverage closure.

Q3What is code coverage? Explain it in detail. What does 100% code coverage mean?5 Marks

Code coverage is a structural (implementation-based) metric that measures how much of the RTL source code has been exercised by the simulation testbench, helping identify unverified/untested parts of the design.

TypeDescription
Statement (Line) coveragePercentage of executable RTL statements/lines executed at least once
Branch (Decision) coveragePercentage of all branches (if-else, case arms) taken in both/all directions
Condition (Expression) coveragePercentage of boolean sub-expressions within a condition that have evaluated to both true and false
Toggle coveragePercentage of signals/registers that have toggled from 0→1 and 1→0 at least once
FSM (State) coveragePercentage of states and state transitions of a finite state machine that have been exercised
Path coveragePercentage of all possible control-flow paths through the code that have been executed

Meaning of 100% Code Coverage

100% code coverage means every line, branch, condition, and toggle in the RTL source code has been exercised at least once by the test suite. However, 100% code coverage does not imply 100% functional correctness — it only confirms that the code was executed, not that its output was checked against the correct expected behaviour for every meaningful scenario, and it says nothing about un-coded (missing) functionality. Hence code coverage must always be supplemented with functional coverage and checkers/assertions for meaningful verification sign-off.

Q4Describe: The Reconvergence Model.5 Marks

The Reconvergence Model describes verification as a process where two independently-derived representations of the same design intent — one from the specification side and one from the implementation side — must be shown to "reconverge" (match/agree) through verification.

Fig: Two independently generated views reconverge and are compared for equivalence
  • One path derives expected behaviour directly from the specification (e.g., a reference/golden model, testbench predictor).
  • The other path is the actual DUT/RTL implementation's behaviour, observed in simulation.
  • Verification compares the two independently-derived results; if they reconverge (agree) for a wide variety of stimuli, confidence in design correctness increases.
  • If they diverge, a bug exists in either the implementation, the reference model, or the specification interpretation.
  • This principle underlies checker/scoreboard-based testbenches, formal equivalence checking, and golden-reference-model comparison.
Q5Explain different Verification Approaches.5 Marks
ApproachDescription
Dynamic (Simulation-based) verificationApplies stimulus to the design in a simulator and checks the resulting output responses; most widely used, but coverage is limited to stimulus applied
Static (Formal) verificationMathematically proves properties of the design (using model checking, equivalence checking) without applying any stimulus — exhaustive for the properties checked
Hardware-assisted verification (Emulation/FPGA prototyping)Maps the design onto emulator/FPGA hardware to run at near real-time speeds, enabling verification of software/firmware and long test sequences impractical in simulation
Hybrid verificationCombines simulation with formal methods (e.g., assertion-based verification) to leverage strengths of both

Each approach trades off exhaustiveness, speed, capacity, and debug visibility differently, and large SoC verification typically uses a combination of all of them.

Q6Draw a flow chart of logic simulation for digital circuit design verification.5 Marks
Fig: Event-driven logic simulation flow chart
  1. Read the design (RTL/gate-level netlist) and the testbench.
  2. Compile and elaborate the design hierarchy.
  3. Apply input stimulus, generating events (signal changes) on the event queue.
  4. Levelize and evaluate all gates/processes affected by the current event.
  5. Update signal values and schedule new events resulting from the change (event-driven simulation).
  6. Repeat until the event queue is empty (or simulation time limit reached); then report results/coverage.
Q7Explain Functional Verification approaches in detail.5 Marks
ApproachDescription
Directed TestingTestbench engineer manually writes specific test cases targeting known functional scenarios; simple but does not scale for complex designs and may miss corner cases
Constrained-Random Verification (CRV)Testbench generates random stimulus constrained to legal/valid input space, automatically exploring a much larger scenario space; combined with functional coverage to measure what has been exercised
Assertion-Based Verification (ABV)Embeds formal properties/assertions (e.g., SystemVerilog Assertions) directly in the design/testbench to continuously check design behaviour during simulation and enable localized bug detection
Coverage-Driven Verification (CDV)Combines constrained-random stimulus with coverage models (functional + code coverage) to drive verification closure — test generation is refined/steered based on coverage gaps
Formal (Model Checking) VerificationMathematically and exhaustively proves that specified properties hold for all possible input sequences, without simulation

Modern SoC verification typically layers these approaches — using CRV+CDV as the primary methodology, supplemented with ABV for local checks and formal methods for critical control logic.

Q8Explain Type I and Type II mistakes during verification.5 Marks

Verification decisions (declaring a design "correct" or "faulty") can go wrong in two distinct ways, analogous to statistical hypothesis-testing errors:

Error TypeDescriptionConsequence
Type I mistake (False Positive / False Alarm)The verification process incorrectly flags a correct design as faulty (e.g., testbench bug, wrong reference model, incorrect assertion)Wastes engineering time chasing a non-existent bug; delays schedule unnecessarily
Type II mistake (False Negative / Missed Bug)The verification process fails to detect a real bug in the design — the design is incorrectly declared "verified"Bug escapes to silicon, potentially causing costly re-spins or field failures — far more serious than a Type I error

Verification methodology aims to minimize both errors, but Type II mistakes (missed bugs) are considered more dangerous, since a Type I error only costs debug time, whereas a Type II error can cause a functional failure that reaches the customer.

Q9Explain following terms with respect to verification: Automation, Poka-Yoke, Redundancy, Equivalence Checking, Model Checking, Design for Verification, Verification Reuse5 Marks
TermDescription
AutomationUse of scripts/tools/regression frameworks to automatically run tests, collect coverage, and report results without manual intervention, improving verification throughput and consistency
Poka-Yoke (mistake-proofing)A design/process technique borrowed from manufacturing that prevents errors by design (e.g., coding guidelines, lint rules, naming conventions) so that certain classes of bugs cannot be introduced in the first place
RedundancyDeliberately duplicating logic/checks (e.g., independent reference model plus RTL) so that an error in one is caught by comparison with the other
Equivalence CheckingA formal technique that mathematically proves two representations of a design (e.g., RTL vs. gate-level netlist after synthesis) are functionally identical, without simulation
Model CheckingA formal verification technique that exhaustively explores the entire reachable state space of a design to prove or disprove that specified properties/assertions always hold
Design for Verification (DFV)Analogous to DFT — designing the RTL with verification in mind from the start (e.g., adding debug/observability hooks, modular partitioning) to make verification easier and faster
Verification ReuseReusing testbenches, verification IP (VIP), assertions, and coverage models across multiple projects/design revisions to reduce redundant verification effort
Q10Discuss: Testing versus Verification.5 Marks
See Q2 above for the detailed comparison table between Testing and Verification.

In brief: Verification asks "Did we build the right design?" (i.e., does the RTL/model correctly implement the intended specification), while Testing asks "Did we build the chip correctly?" (i.e., is the manufactured silicon free of physical defects). Verification is a pre-silicon, one-time design-correctness activity; testing is a post-silicon, per-unit manufacturing-quality activity. Both are essential and complementary — a perfectly tested (defect-free) chip built from an unverified (buggy) design will still fail in the field, and a perfectly verified design fabricated with defects will also fail without proper testing.

Q11Explain the Role of Verification Plan.5 Marks

The verification plan acts as the master roadmap that drives the entire verification effort, playing the following key roles:

  • Scope definition: Clearly enumerates every feature, mode, and corner case of the design that must be verified, preventing gaps in coverage.
  • Strategy selection: Specifies which verification approach (simulation, formal, emulation) and methodology (CRV, ABV, etc.) will be used for each feature.
  • Resource & schedule planning: Enables accurate estimation of engineering effort, tool licenses, and timeline for verification closure.
  • Traceability: Maps specification requirements to test cases/checks, ensuring every requirement is verified and providing an audit trail.
  • Sign-off criteria: Defines measurable coverage goals (code + functional coverage, bug rate trends) that determine when verification is considered complete.
  • Communication: Serves as a common reference document reviewed by design, verification, and architecture teams to align expectations.
Q12List different criteria for Verification Plan.5 Marks
  • Feature list: Complete list of design features/functions requiring verification, derived from the specification.
  • Verification environment architecture: Testbench structure, required Verification IP (VIP), interfaces/protocols to support.
  • Test/stimulus strategy: Directed vs. constrained-random test approach for each feature.
  • Coverage model: Code coverage and functional coverage points/goals to be tracked.
  • Checking strategy: Assertions, scoreboards, reference models used to check correctness.
  • Regression & automation strategy: How tests are run, tracked, and re-run on every design change.
  • Bug tracking & triage process: How discovered bugs are logged, prioritized, and closed.
  • Sign-off/exit criteria: Target coverage percentage, acceptable open-bug severity, and schedule milestones for declaring verification complete.
Q13Explain different Levels of Verification.5 Marks
Fig: Verification is carried out at increasing levels of integration
LevelDescription
Unit / Module LevelVerifies a single small RTL module in isolation with a dedicated testbench — earliest, fastest, highest controllability/observability
Block / IP LevelVerifies a functional IP block (e.g., a UART, cache controller) composed of multiple modules, including its interfaces
Sub-system LevelVerifies interaction between multiple IP blocks connected together (e.g., a bus fabric with several masters/slaves)
System / Chip (SoC) LevelVerifies the complete integrated chip, including software/firmware interaction, power management, and full-chip use-case scenarios

Bugs are progressively cheaper and easier to find and fix at lower levels (unit/block), motivating a "verify early, verify often, bottom-up" strategy before full system-level integration.

Q14Describe Verification Strategies.5 Marks
  • Bottom-up strategy: Verify individual modules/blocks first, then progressively integrate and verify at sub-system and system level — catches bugs early and cheaply.
  • Top-down strategy: Begin verification at the system level using behavioural/abstract models before detailed RTL is ready, useful for early architecture validation.
  • Coverage-driven strategy: Define coverage goals up front and drive constrained-random stimulus generation to systematically close coverage gaps.
  • Regression-based strategy: Maintain a growing suite of automated regression tests re-run on every RTL change to catch regressions (newly introduced bugs) immediately.
  • Layered/reuse strategy: Build modular, reusable verification environments (VIP, testbenches) that can be reused/scaled from block to system level, minimizing duplicated effort.
  • Formal-assisted strategy: Apply formal methods (model checking, equivalence checking) selectively to control-dominated or safety-critical logic, complementing simulation-based verification.

A well-planned verification effort typically combines several of these strategies, guided by the verification plan, to balance thoroughness, schedule, and resource constraints.
